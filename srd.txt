# 1. Executive Summary

Bublix Shipping is a centralized logistics and shipment management platform designed to manage domestic and international shipping operations.

The platform will provide:

1. Public corporate website.
2. Public shipment tracking.
3. Central administration dashboard.
4. Branch and warehouse management.
5. Shipment creation and management.
6. Domestic and international shipment processing.
7. Financial and multi-currency management.
8. Driver and delivery management.
9. Merchant and business customer management.
10. Shipping documents and automated printing.
11. Notifications and customer communication.
12. API infrastructure for future Flutter mobile applications.

The system will initially operate from one branch while supporting multiple branches and countries through its database and business architecture.

# 2. Business Requirements and Scope

## 2.1 Business Model

Bublix Shipping will support two main shipping categories:

### A. Domestic Shipping

- Shipments within the same country.
- City-to-city deliveries.
- Branch-to-branch transfers.
- Local pickup and delivery.
- Local pricing rules.
- Local currency transactions.

### B. International Shipping

- Shipments between different countries.
- Origin and destination country management.
- International shipping routes.
- Air, sea and land shipping services.
- Customs clearance information.
- Commercial invoices.
- Customs and additional shipping charges.
- Multiple currencies.
- International tracking events.

## 2.2 Branch Expansion Strategy

The first operational deployment will use one branch.

However, the architecture must support:

- Multiple branches.
- Multiple warehouses.
- Different countries.
- Branch managers.
- Branch employees.
- Inter-branch shipment transfers.
- Branch-specific pricing where authorized.
- Independent financial reports per branch.

Every shipment must identify its origin and destination branches or hubs where applicable.

## 2.3 Language Support

The platform will support:

- English (EN).
- Arabic (AR).
- RTL and LTR layouts.
- Language switching without losing the current page.
- Translated shipment status descriptions.
- Localized dates and numbers.
- Currency formatting.

**Important:** The administration dashboard and public website will be bilingual, while shipping documents such as Waybills and Commercial Invoices will remain English-only in the initial version.

## 4.4 Database Design Standards

1. UUID primary keys.
2. Foreign key constraints.
3. Unique tracking numbers.
4. Indexed tracking numbers.
5. DECIMAL for financial values.
6. ISO 4217 currency codes.
7. UTC timestamps stored in the database.
8. Explicit local timezone configuration per branch.
9. Soft deletion where appropriate.
10. Immutable shipment event history.
11. Database transactions for financial and shipment operations.
12. Proper indexes on frequently queried fields.

Financial amounts must retain their original currency and exchange-rate snapshot. Currency conversion must never silently change the original transaction amount.

# 5. Shipment Management and Tracking

## 5.1 Tracking Number

Automatically generate unique tracking numbers using:

`BBLX-XXXXXX`

The system must guarantee uniqueness even when multiple employees create shipments simultaneously.

## 5.2 Shipment Lifecycle

Initial shipment statuses:

| Status | Description |
|---|---|
| CREATED | Shipment created |
| PICKED_UP | Collected from sender |
| AT_ORIGIN_HUB | Arrived at origin hub |
| IN_TRANSIT | Moving between locations |
| AT_DESTINATION_HUB | Arrived at destination hub |
| CUSTOMS_CLEARANCE | Under customs processing |
| OUT_FOR_DELIVERY | Assigned for delivery |
| DELIVERED | Successfully delivered |
| ON_HOLD | Temporarily held |
| DELIVERY_FAILED | Delivery unsuccessful |
| RETURNED | Returned to sender |
| CANCELLED | Shipment cancelled |

Not every status applies to every shipment type. Valid status transitions must be controlled by backend business rules.

## 5.3 Tracking Event Requirements

Every event must include:

- Shipment ID.
- Event status.
- Location.
- Branch or hub ID, when applicable.
- Event timestamp.
- Employee or driver ID.
- Notes.
- Public visibility flag.

Tracking events must be append-only. Corrections should create an auditable correction record rather than silently deleting previous events.

## 5.4 Public Tracking

Customers can track shipments using their tracking number.

Public tracking will show:

- Tracking number.
- Shipment type.
- Current status.
- Origin and destination cities.
- Shipment timeline.
- Last known tracking location.
- Estimated delivery date when available.

Private details such as receiver phone, complete address, personal information and financial records must remain hidden.

# 6. Pricing Engine

The pricing engine must support both domestic and international shipping.

Pricing rules may depend on:

- Origin country.
- Destination country.
- Origin city.
- Destination city.
- Shipping service.
- Actual weight.
- Volumetric weight.
- Chargeable weight.
- Shipment dimensions.
- Distance or shipping zone.
- Merchant contract.
- Additional services.

## 6.1 Weight Calculation

Volumetric weight formula:

`Length × Width × Height / Divisor`

The divisor must be configurable by service and transport method.

Chargeable weight:

`MAX(Actual Weight, Volumetric Weight)`

## 6.2 Pricing Examples

- Domestic delivery: based on weight and delivery zone.
- International air: based on chargeable weight.
- Sea shipping: based on CBM or agreed freight pricing.
- Express shipping: based on service level and weight.

The public quotation calculator and internal shipment creation must use the same pricing engine.

A confirmed quotation must preserve the price and currency used when it was generated.

# 7. Financial and Payment Management

## 7.1 Supported Payment Methods

- CASH
- COD
- BANK_TRANSFER
- MOBILE_MONEY

Visa and Mastercard are not included in the initial approved payment scope.

## 7.2 Important Financial Distinction

The system must separate:

**Shipping Charges:** The amount owed for the shipping service.

**COD Amount:** The value collected from the receiver on behalf of the sender or merchant.

These must not be combined into one financial amount.

Example:

- Shipping fee: USD 15
- COD amount: USD 100
- Total collected from receiver: USD 115

The system must record USD 15 as the shipping charge and USD 100 as COD collection, with separate financial allocations and settlement records.

## 7.3 Multi-Currency Support

Supported initial currencies:

- USD
- UGX
- SDG
- AED

The system must allow additional currencies through configuration.

Each financial transaction must store:

- Amount.
- Currency.
- Exchange rate, if converted.
- Base currency equivalent, if applicable.
- Transaction date.
- Branch.
- Payment method.
- Reference number.
- Recorded by.
- Verification status.

## 7.4 Payment Verification

Bank transfers and mobile-money transactions may initially be recorded manually.

The system should support:

- Transaction reference.
- Payment proof upload.
- Verification by authorized accountant.
- Approved or rejected status.
- Audit history.

### A.2 Recommended Shipment Structure

The Shipments table must include:

**Identification**
- id: UUID
- trackingNumber: Unique string
- organizationId: UUID
- shipmentType: DOMESTIC / INTERNATIONAL
- serviceTypeId: UUID

**Sender**
- senderCustomerId: UUID
- senderNameSnapshot: String
- senderPhoneSnapshot: String
- senderAddressSnapshot: JSONB

**Receiver**
- receiverName: String
- receiverPhone: String
- receiverEmail: String, optional
- receiverAddress: JSONB

**Routing**
- originCountryId: UUID
- destinationCountryId: UUID
- originHubId: UUID
- destinationHubId: UUID
- currentHubId: UUID, nullable

**Package Information**
- actualWeight: DECIMAL
- volumetricWeight: DECIMAL
- chargeableWeight: DECIMAL
- totalPieces: INTEGER
- declaredValue: DECIMAL
- declaredCurrency: CHAR(3)

**Financial Information**
- shippingCost: DECIMAL
- additionalCharges: DECIMAL
- discountAmount: DECIMAL
- totalAmount: DECIMAL
- currency: CHAR(3)
- paymentMethod: ENUM
- paymentStatus: ENUM
- codAmount: DECIMAL
- codCurrency: CHAR(3)

**Operational Information**
- shipmentStatus: ENUM
- estimatedDeliveryDate: DATE
- specialInstructions: TEXT
- createdBy: UUID
- createdAt: TIMESTAMP
- updatedAt: TIMESTAMP

Sender and receiver snapshots preserve the original shipment information even if the customer's saved profile changes later.

### A.3 Important Design Rules

1. Store each shipment package separately in ShipmentItems.
2. Store every tracking movement in ShipmentEvents.
3. Never overwrite historical shipment events.
4. Keep shipment charges separate from payments.
5. Keep COD collections separate from shipping revenue.
6. Keep exchange rates associated with the actual transaction.
7. Use database transactions for shipment creation, invoice creation and payment recording.
8. Use unique constraints for tracking numbers and invoice numbers.
9. Add indexes on trackingNumber, shipmentStatus, originHubId, destinationHubId and createdAt.
10. Use a consistent organizationId for company-owned records.

| GET | /reports/customers | Customer reports |

# C. API ENGINEERING STANDARDS

## C.1 Pagination

All list endpoints must support:

- page
- limit
- search
- sortBy
- sortOrder
- status
- startDate
- endDate

## C.2 Authentication

All private endpoints require a valid access token.

Authorization must be checked at the backend service layer.

## C.3 Idempotency

Financial and shipment creation endpoints should support an Idempotency-Key header to prevent duplicate operations when clients retry requests.

## C.4 Shipment Creation Transaction

Shipment creation must execute as a single logical database transaction:

1. Validate sender and receiver.
2. Validate origin and destination.
3. Calculate pricing.
4. Generate unique tracking number.
5. Create shipment.
6. Create shipment items.
7. Create initial tracking event.
8. Generate invoice when applicable.
9. Commit database transaction.

External notifications and PDF generation should be handled after successful database commit through background jobs.

## C.5 Tracking Event Transaction

When updating a shipment:

1. Verify user authorization.
2. Validate the permitted status transition.
3. Update the current shipment status.
4. Insert a new ShipmentEvent.
5. Record the acting user.
6. Commit transaction.
7. Trigger notification asynchronously.

## C.6 Financial Transaction Rules

- Payments must be independently recorded.
- COD collections must be independently recorded.
- Payment verification must be auditable.
- Settlement must be traceable.
- Financial records must not be silently deleted.
- Refunds and reversals must be recorded as separate transactions.

## C.7 API Documentation

Use OpenAPI 3.1 / Swagger.

The API documentation must include:

- Authentication requirements.
- Endpoint descriptions.
- Request schemas.
- Response schemas.
- Validation errors.
- Permission requirements.
- Example requests.
- Example responses.

Swagger should be available in the development environment and restricted appropriately in production.
